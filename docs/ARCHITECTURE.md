# Architecture

FastAPI + synchronous SQLAlchemy 2 sessions + Psycopg 3; Alembic owns schema changes. React + TypeScript + Vite + React Router + TanStack Query; native fetch; Tiptap for formatted teaching content.

One Postgres database. Each feature owns commands (writes/transactions) and queries (authorized projections). No bus, generic repository, event sourcing, separate read database, or runtime schema repair.

Opaque hashed server sessions, HttpOnly cookies and session CSRF tokens; Argon2 passwords. Parent/child resources are scoped by authenticated role, offering ownership/enrollment and section targeting. Restricted fields must never enter student responses.

Teacher accounts carry an optional `account.college_id` foreign key to `college.id`. Admin account listing/count queries accept `college_id`; teacher invitations and reviewed imports store the selected active college. Admins can update or clear a faculty account's college through `PATCH /api/accounts/{id}/college`; this operation is audited. College deletion is refused while a teacher is assigned. Faculty assignment filters use this account association rather than deriving faculty college from their current offering sections.

Accounts store `first_name`, `middle_name`, `last_name`, and `suffix` separately. `display_name` remains the compatible read/search projection and is generated as `LAST NAME, FIRST MIDDLE INITIALS, Suffix` (for example, `DELA CRUZ, JUAN A., Jr`). Student names in the existing database are backfilled from the roster workbook only when student number and normalized full name both match; other accounts use the approved suffix/space-and-surname-particle fallback. Account invitations and imports accept/store the name components; the teacher import also retains support for legacy full-name files. Name edits preserve the components.

Admins edit teacher name, email, and college/program through `PATCH /api/accounts/{id}/profile`. Changing email revokes the teacher's sessions, invalidates outstanding links, and requires a new invitation verification. Taking over an existing offering updates its faculty in place; enrollment and academic records remain attached to the same offering, and `offering.faculty_transferred` audits the previous and replacement teacher. A replacement must be active, and duplicate subject assignments for the same teacher and term are refused.

Migration `4e6a81c0b932` backfills every existing faculty account to the administrator-selected default college `d81b2a06-85a9-44d0-9f50-41d7fbc76f7f`.

Files remain outside webroot and are delivered by an authorized API. Drafts use compare-and-swap revisions; published documents and grade snapshots are immutable.

Syllabus outlines may mark one chapter as the subject introduction. If present, the introduction must be the first chapter; ordinary chapters follow it, and chapter numbering excludes the introduction.

Grading-policy JSON may restrict `online_quiz_categories` and `activity_categories` to category keys defined by that same policy. An omitted or null list is treated as unrestricted for compatibility with existing syllabus revisions; an explicit empty list allows no graded work of that type. Faculty assessment editors show only allowed categories, and assessment publication plus bulk planning independently enforce the restriction. Publishing a syllabus revision is refused if it would make any existing published graded assessment invalid.

Faculty Classwork chapter-level creation anchors new learning items and assessments to the selected chapter before opening their editors. Assessment creation validates the anchor against the offering's current draft or published syllabus; AI-generated quizzes follow the same validation. Creation dialogs display the chapter hierarchy rather than offering an independent chapter selector. AI quiz source selection groups published readable materials by syllabus chapter, lets teachers select individual materials or all materials in a chapter, and retains a bounded total source-text budget.

Online quiz scores are computed only from submitted attempts. Faculty may correct a submitted answer, which recomputes the score, but cannot enter or overwrite a quiz score through individual-score or gradebook batch APIs.

Online quizzes expose one active question at a time. Each published question carries a teacher-configured time limit, stored in seconds. `quiz_question_clock` records the server-side start, expiry, and terminal state (`answered`, `skipped`, or `timed_out`); a refresh or disconnected client cannot pause or reset a deadline. The server accepts answers only for the active question and starts the next question at the skip/answer time or prior expiry time. Students cannot revisit locked questions. Assessment availability and overall deadlines remain enforced.

The admin uploads a prospectus either to an existing active college or while creating a new college. Upload, extraction, college creation (when selected), and subject creation commit atomically; there is no user-facing review step. Unreadable/invalid subject rows reject the entire upload. Newly created subjects inherit the selected college; a subject is skipped only when its code is already in that same college's catalog, and existing entries are not overwritten. The same code may exist in another college as a separate subject. Subject-code uniqueness is enforced per college (and globally only for legacy subjects without a college). The legacy reviewed-import API remains available for compatibility. After upload, the admin returns to the prospectus catalog and sees the result in a dialog. The existing-subject Edit dialog can update placement (year level and semester) and college through the subject update command. New manual subjects inherit the selected active college and the year/semester of the Add subject section; those fields stay locked in the Add dialog.

Approved schema/lifecycles: IMPLEMENTATION_PLAN.md sections 3-4. AI retrieval restrictions: section 6.

## Academic calendar lifecycle

School-year creation validates a consecutive year label, ISO dates, year/date consistency, semester containment and sequence, and creates one school year plus exactly two draft semesters in one transaction. Semester ranges may be adjacent or may have enrollment-preparation gaps between them; they cannot overlap. Friendly overlap checks are backed by PostgreSQL exclusion constraints on inclusive date ranges; a partial unique index permits at most one active semester. Status values are `draft`, `scheduled`, `active`, `inactive`, and `archived`. Draft, scheduled, and active semester calendar details may be edited; an active semester's edited dates must continue to contain today's date in the configured school timezone. Every edit also preserves school-year containment and semester order/non-overlap. Only active allows normal role-authorized academic writes. Scheduling is an audited command. An administrator may immediately activate a scheduled semester from its Settings card; the command checks that no other semester is active and that the previous semester is closed where applicable. A timezone-aware API-lifespan job also activates a scheduled term on its start date and closes it after its end date, recording system-attributed audit events; missed scheduled terms are marked inactive rather than activated late. An inactive semester may be reopened only within its scheduled dates in the configured school timezone, and only when no other semester is active. Reopening requires a reason, restores `active`, and is audited; archived semesters cannot be reopened.

Migration `c91f7a2e4b60` performs the one-time, forward-only reset of every existing semester status to `draft`, including active, scheduled, inactive, and archived terms. It preserves school-year/calendar dates, academic records, and closure metadata. No semester remains active after this migration; administrators must schedule one, then may activate it immediately from Settings or allow automatic activation on its start date. A schema downgrade does not restore pre-migration statuses.

Section deletion is admin-only and limited to an active term. The command locks the section and refuses deletion while any roster history, enrollment, offering, targeted content or announcement, teaching coverage, assessment assignment, or attendance record references it.

The admin term workspace presents student management with a college/program filter (displayed as “Course”), prospectus-year, and section filters. Sections belong directly to a college/program and the filter scopes the roster to sections owned by that college; subject offerings are assigned separately in Offerings. The Add sections dialog generates names from the selected college code and year level (for example, `BSE 1A`), without creating or changing offerings. Historical sections are associated with a college only when their existing offerings identify exactly one college; ambiguous sections remain unassigned. Roster profile edits are inline and server-scoped to an active membership in an open term. Changing a student's email revokes sessions and outstanding links, returns the account to invitation-pending, and sends a verification invitation to the new address. The dedicated section-student page retains candidate selection, withdrawal, and history workflows.

`POST /api/sections/{section_id}/students` is admin-only and creates an invitation-pending student account plus active section membership in one transaction. It requires the section's term to be active, rejects duplicate email/student numbers, audits both account invitation and membership, and queues invitation email delivery after commit.

### Additions: learning order, paging and chat deletion
- `learning_item.position` orders items inside a chapter/topic; students read them in syllabus order, then position (`teaching/items.ordered_published`, the single source for the lesson list, the dashboard next step and the Next link). `PUT /api/teach/offerings/{id}/items-order` reorders one group. Learner payloads add `completed`, `up_next`, `next_lesson`; work payloads add `bucket` and `late_allowed` (`assessments/learner.bucket_of`, shared with the dashboard).
- Paging: `GET /api/admin/issues` takes `page`, `page_size` (max 100), `status`, `type`, `q` and returns `total`; study conversations and messages take `limit` and a `before` timestamp cursor and return `has_more` / `has_earlier`; announcements take `limit`.
- `DELETE /api/learn/offerings/{id}/study/conversations/{cid}` hard-deletes the student's own conversation (allowed after withdrawal or term close).

## Study slice (Milestone 5)

`features/study` owns derived study text (`content_chunk`, from published learning-item revisions only), private conversations, reference-link text snapshots, AI quiz generation records, lesson completions and progress events. It calls `teaching` and `assessments` only through their access helpers and models; `assessments` calls only `study.events.record_event`, which has no other imports, to avoid cycles.

All provider traffic goes through `study/provider.py` (safe error codes, no provider bodies). Retrieval (`study/retrieval.py`) is the single place that decides what the model may read; chat and quiz generation use separate pipelines. AI quiz drafts are ordinary unpublished assessment drafts flagged `ai_generated`, published only when `reviewed_counter == draft_counter`. Progress events are unique per (student, type, ref) and are written in the same transaction as the action that earned them. Details: `docs/AI.md`, `docs/DECISIONS.md`.

## Exports, support and backup (Milestone 6)

`features/exports` builds one format-independent table per request (`tables.py`: published releases from their own snapshots, or a working preview marked as such) and renders it to real XLSX/PDF (`render.py`); the router is faculty-only and audits each download. `features/support` holds issue reports (students/faculty create, administrators review). `app/backup.py` computes the manifest and verifies restored copies; `scripts/` orchestrates Docker/pg_dump/restore around it. Browser verification lives in `frontend/e2e/` (headless Edge via playwright-core). Commands and results: `docs/OPERATIONS.md`, `docs/ACCEPTANCE.md`.

### UX rework, Phase 1 (skeleton-first setup)
`assessments/planning.py` owns three commands, all faculty-only and scoped to the teacher's own offering: `POST /api/teach/offerings/{id}/assessments/plan` creates up to 30 hidden draft assessments in one transaction (idempotent through a `plan_key` stored in the audit event; category and period are checked against the draft or published policy), `PUT /api/teach/offerings/{id}/schedule` stores `offering.meeting_days` (bitmask, Monday = 1, migration `29f75f29e858`), and `POST /api/teach/offerings/{id}/copy-from/{source_id}` copies one of the teacher's own earlier subjects into an EMPTY one as drafts only (syllabus draft, lessons, links, files with their bytes duplicated, assessments with questions; never sections, dates, attempts, scores, submissions, students, announcements or attendance). Offering summaries carry `meeting_days`.

### UX rework, Phase 2 (steppers and question entry)
`assessments/question_import.py` parses pasted plain text into questions (multiple choice from lettered choices, true/false from an answer of True or False, short answer with accepted answers separated by `|`; optional `Points:` and `Why:`), returns valid blocks and reports every problem block by line number, and never guesses. `POST /api/teach/offerings/{id}/assessments/parse-questions` previews it without saving; the teacher adds the questions to the draft explicitly. `POST /api/teach/offerings/{id}/assessments/{aid}/duplicate` makes a hidden draft (same settings and questions, title prefixed "Copy of", sections kept, dates and records never copied; an AI-drafted source stays flagged so it needs review again). The assessment editor is a three-step stepper for online quizzes (Basics, Questions, Review and assign) and one short screen for the other kinds; the publish button's label follows the state: Assign, Add to gradebook (teacher-scored kinds), Update for students.

### Online quiz attempts
Attempt answers are saved per question and may be changed until submission. The question-number navigator is presentation state; the server accepts any answer belonging to the attempt's published revision. Existing timer columns and clock rows are legacy data retained but are not read or written. Submission scores saved responses and closes the attempt. Student projections return question prompts and public choices but never accepted answers or explanations. Quiz availability and deadlines remain server-enforced.

### UX rework, Phase 3 (grades and publication)
`PUT /api/teach/offerings/{id}/gradebook/scores` (`assessments/gradebook_edit.py`) saves up to 500 gradebook cells in one transaction, ALL OR NOTHING: each cell runs through `scores.apply_score` (the single-score rules without the commit: published, student applies, not above the maximum, quiz rules, expected revision); if any cell is rejected the transaction is rolled back and a 409 `batch_rejected` lists every rejected cell in `error.field_errors`, keyed `assessmentId:studentId`. `app.errors.fail` accepts an optional `fields` dict that the error handler passes through. `faculty_rows` carries `to_return` (a scored result the student does not yet see exactly as it is), which drives "Return N graded results". The UI replaces every native `confirm()` with `components/confirm.tsx` (promise-based, Cancel first and focused, `data-confirm` / `data-confirm-yes` / `data-confirm-no` for scripts) and uses `components/undo.tsx` (a persistent live region with a 10-second Undo) for reversible removals of a question, a chapter and the grading policy. Publishing grades is a review-then-publish dialog computed from the working values already on the page.

The Gradebook also offers an icon-only return action in each assessment header while a scored result is unreleased. It reuses the existing confirmation and `POST /api/teach/offerings/{id}/assessments/{aid}/release`; it is separate from publishing period or course grades.

`POST /api/teach/offerings/{id}/gradebook/manual-columns` atomically creates and publishes a faculty-scored `manual` assessment from title, maximum points, a non-attendance category, and a policy period. It is an all-section gradebook column, reuses `assessment_score` and the normal grade calculation, audits creation/publication, and flags affected published grades for review. Its transaction serializes with overall grade publication so snapshots do not race the new column. The faculty-only endpoint requires an active offering and a valid published grading policy.

### UX rework, Phase 4 (attendance grid)
`GET /api/teach/offerings/{id}/attendance` returns the existing sessions and roster plus the published policy's attendance scoring settings. The faculty attendance page now offers status-only entry controls; previously recorded numeric marks remain available to grade calculations and exports. `PUT /api/teach/offerings/{id}/attendance` remains a PARTIAL save per (section, date): only the students named in `marks` change (null clears). Syllabus publication rejects a maximum below an existing numeric mark. The `attendance_mark` row stores exactly one of status or numeric points (migration `8a6e4c1d9f23`); existing status rows are preserved. A date's grading period is locked once recorded (409 `period_locked`). The grid depends on exactly that and `tests/test_attendance_grid.py` pins it. The grid's columns are the dates in the visible week or month that are recorded, fall on a class day (`offering.meeting_days`), or were added by hand; they are computed in the browser, so nothing is stored for a date until a mark is saved. Each cell change is debounced per date (600 ms) into one partial save; a failed save keeps the typed value, outlines the cell and offers Retry; leaving the page tries to flush first (`useFlushOnLeave`). There is no per-cell version check: two tabs editing the same cell are last-write-wins, as before.

The Gradebook query projects recorded attendance sessions as read-only columns grouped by date and grading period across the offering's sections. Headers display `MM/DD/YY` and retain the full date in their tooltip. Each date uses the policy's configured maximum; status and numeric entries show the same points used by `attendance_category`. Excused entries are excluded only when the policy leaves excused points unset. The category weight is applied once in the period calculation, not divided among dates. Unmarked entries have no points. A fresh query reflects changed, cleared, or deleted sessions. This is a display-only projection, not a second set of score inputs. The Gradebook's Edit grading categories action opens the subject-setup wizard at Grading, reusing the existing draft or creating a recoverable one from the published syllabus.

Syllabus file replacement uses the existing faculty `POST /api/teach/offerings/{id}/syllabus/import` endpoint. DOCX/PDF content becomes a new reviewable draft; the published revision remains visible until normal draft publication, and the current published grading policy is carried into the draft. An existing draft must be resolved before importing, preserving recoverability and avoiding silent draft replacement.

## Phase 5 endpoints
- `GET /api/dashboard/faculty/review`: activity submissions waiting for a grade across the teacher's subjects, oldest first.
- `GET /api/teach/offerings/{id}/exports/attendance?format=xlsx|pdf&section_id=&start=&end=`: attendance file for one section (teacher of the offering only; recorded dates only; audited without names).
- `POST /api/teach/offerings/{id}/assessments/{aid}/unpublish`: published revision becomes superseded and a draft is kept or created; refused with 409 `has_history` once attempts, uploads, scores, released results or exceptions exist.

## Bulk assignment and the paginated section roster
- `POST /api/terms/{id}/offerings/bulk` `{faculty_id, items:[{subject_id, section_ids, placement_override_reason?}]}`: one teacher, several subjects, each with its own sections, all or nothing. A refusal names the subject and saves nothing; the same subject twice is `duplicate_subject`. Single `POST .../offerings` and `PATCH /offerings/{id}` are unchanged.
- `PUT /api/faculty-imports/{id}` edits only the staged faculty-import rows already in the preview, then revalidates against accounts and other rows; adding/removing rows is refused. Commit remains atomic if any row is invalid.
- `DELETE /api/offerings/{id}` archives an assignment (with an audit event) without deleting enrollment/history, and is refused while any enrollment is still active. `POST /api/offerings/{id}/restore` restores an archived assignment. Both operations require an active term and admin authorization.
- `GET /api/sections/{id}/roster?page&page_size&search&status=active|withdrawn|all`: a section's students a page at a time (admin only).
- `GET /api/sections/{id}/candidates?page&page_size&search&account=all|active|invited`: students who can be added, excluding anyone already active in a section of the same term.
- `DELETE /api/sections/{id}/members/{student}?reason=` now requires a reason (3 to 1000 characters, 422 `reason_required`); it is stored in the `section.member_withdrawn` audit event.
- Admin route `/admin/terms/:termId/sections/:sectionId/students` (the old Manage students dialog is gone).

## Files and links as lessons (Phase 6)
- Lessons, files and links are one sequence (`SEQUENCE_KINDS` in `teaching/items.py`): each can be marked done through the same `POST /api/learn/offerings/{id}/lessons/{item}/complete` (idempotent, one `lesson_completed` event per student and item), each is a progress step (steps now carry `kind`), "Up next" and "Next lesson" run through all three (`next_lesson` and `first_incomplete` carry `kind`). Chat grounding and the chat's "Next in your lessons" suggestion are unchanged.
- `GET /api/files/{id}/preview`: inline delivery for course material only, and only when the stored type is PDF, PNG or JPEG AND the first bytes match that type; same access rule as download (so unpublished, archived, other-section and other-teacher files are 404); `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src 'self' data:; frame-ancestors 'self'`, `no-store`. Everything else, and `/download`, stays an attachment (now also `nosniff`).
